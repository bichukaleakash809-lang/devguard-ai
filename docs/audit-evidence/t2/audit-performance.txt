Audit append performance defect — evidence
Captured: 2026-07-30T00:38:59Z

DEFECT: _read_last_entry() iterated EVERY line of the audit log to find
prev_hash, on every append. Its docstring said 'Streaming, not full-load' —
true of memory, false of I/O. Since it runs once per append, writing N
entries cost O(N^2). It also ran synchronously inside append_entry's lock,
so the cost was paid on the asyncio event loop and stalled unrelated
requests, not just audit writes.

MEASURED — mean ms per append, 20 appends, by pre-existing log size:

  existing entries   BEFORE      AFTER
  ----------------   --------    --------
               0      0.112 ms    0.379 ms
           1 000      0.338 ms    0.314 ms
          10 000      2.738 ms    0.405 ms
          50 000     13.823 ms    0.368 ms

Before: 123x degradation from empty to 50k entries, growing without bound.
After:  flat. 37x faster at 50k, and it no longer degrades.

HONEST TRADEOFF: the empty-log case is ~0.27 ms slower, because the file
work now goes through asyncio.to_thread. That is the cost of not blocking
the event loop, and it is a fixed cost rather than a growing one.

covered by tests rather than trusted:

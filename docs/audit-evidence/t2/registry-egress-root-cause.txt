Captured: 2026-07-30 (session HTTPS_PROXY=http://127.0.0.1:39233)

Supersedes the diagnosis in registry-egress-diagnosis.txt on two points, both
corrections rather than refinements:

  1. That file said the blocker could only be lifted by an administrator adding

--------------------------------------------------------------------------------
0. SUMMARY
--------------------------------------------------------------------------------

ROOT CAUSE: The egress policy gateway is default-deny. Docker Hub's registry
API and auth hosts ARE allowed; its blob/CDN host is NOT. So every `docker pull`
authenticates successfully, resolves the manifest successfully, and then fails
at the layer download.

    ALLOWED   registry-1.docker.io, index.docker.io, auth.docker.io
    DENIED    production.cloudfront.docker.com      <- the entire blocker

MINIMUM CHANGE: none to this repository, and none to the environment policy.
A three-line `/etc/docker/daemon.json` pointing Docker at `mirror.gcr.io` —
which is already allowed — makes every canonical image name resolve. Verified
end to end in §6.

3. THE SEVEN DIAGNOSTIC QUESTIONS, ANSWERED

1. DOCKER REGISTRY CONNECTIVITY — API reachable, CDN not.

    https://index.docker.io/v2/                 401   unauthenticated answer)
    https://auth.docker.io/                     404   reachable

2. DOCKER HUB AUTHENTICATION — works, and is NOT the cause.

   Hub credentials would NOT help, because an authenticated pull is redirected

   production.cloudfront.docker.com.

5. THE FINDING THAT CHANGES THE ANSWER: mirror.gcr.io IS ALREADY ALLOWED
--------------------------------------------------------------------------------

Other registries were surveyed to see whether any usable path existed:

    ghcr.io               401   allowed        quay.io            000   denied
    public.ecr.aws        401   allowed        registry.k8s.io    000   denied
    gcr.io                401   allowed        docker.elastic.co  000   denied
    registry.gitlab.com   401   allowed        nvcr.io            000   denied

`mirror.gcr.io` matters for a structural reason: unlike Docker Hub, it does NOT
redirect blobs to a separate CDN hostname. Its redirect is RELATIVE, so the
bytes come from the same already-allowed host:

    Location: /artifacts-downloads/namespaces/artifact-registry-docker-cache/

the redirect:

6. MINIMUM REMEDIATION — VERIFIED, ZERO REPOSITORY CHANGES
--------------------------------------------------------------------------------

Pulling `mirror.gcr.io/signoz/signoz:latest` works but renames the image, which
would mean editing casting.yaml.lock and docker-compose.yml. That is avoidable.
A daemon-level mirror keeps every canonical name intact.

/etc/docker/daemon.json (the whole file — the directory exists and is empty):

    {
      "registry-mirrors": ["https://mirror.gcr.io"]
    }

Then restart the daemon. Confirmed registered:

    $ docker info | grep -A1 "Registry Mirrors"
     Registry Mirrors:
      https://mirror.gcr.io/

CONTROLLED BEFORE/AFTER — the SAME command, minutes apart:

    BEFORE (no daemon.json)
    $ docker pull redis:7-alpine
    7-alpine: Pulling from library/redis
    failed to copy: ... "https://production.cloudfront.docker.com/...": Forbidden
    EXIT 1

    AFTER (daemon.json above, daemon restarted)
    $ docker pull redis:7-alpine
    Digest: sha256:e7723ff73d963f5cc6d9c4643ea3d989527a402a319239054e9472a7fb9219a2
    Status: Downloaded newer image for redis:7-alpine
    docker.io/library/redis:7-alpine
    EXIT 0

Note the resulting tag: `docker.io/library/redis:7-alpine` — the CANONICAL
name, and the digest is the Docker Hub digest from the §5 table. Also verified
for a namespaced (non-`library/`) image:

    $ docker pull signoz/signoz:latest
    Digest: sha256:9b0ea7ad66485c2e53d158108dc7d75cd6e14f0cfd129eb342b3889ed5a968ce
    Status: Downloaded newer image for signoz/signoz:latest
    docker.io/signoz/signoz:latest
    EXIT 0

So `casting.yaml.lock` and `docker-compose.yml` need NO edit. No repository file
changes. No architecture change. No production code change.

CAVEAT, stated because it matters: this container is ephemeral. `daemon.json`
is environment state and does not survive a new session, and nothing in this
repository recreates it. It is a per-session setup step, not a committed fix.

ALTERNATIVE REMEDIATION (if the owner prefers to fix the policy rather than
route around it): allowlist ONE hostname.

    production.cloudfront.docker.com          <- unblocks all eight images

HOSTNAMES, NOT IPs. The IPs observed this session were stable across repeated
resolution (13.226.251.23/.56/.95/.123 for the CloudFront host; 74.125.126.82
for mirror.gcr.io) but both are anycast CDN edges that vary by client location
and rotate over time. An IP allowlist would break without warning. Requested as
hostnames, per instruction.

7. WHAT IS STILL BLOCKED FOR §6.1 — AND IT IS NOT THE IMAGES
--------------------------------------------------------------------------------

The images are no longer the obstacle. The DEPLOYMENT TOOL is.

`casting.yaml` / `casting.yaml.lock` are SigNoz **Foundry** manifests, driven by
`foundryctl`, which is not installed. Both documented install routes are shut,
and — importantly — for TWO DIFFERENT REASONS:

  a) The install script, per SigNoz/foundry's own getting-started.md:
         curl -fsSL https://signoz.io/foundry.sh | bash
     `signoz.io` is DENIED BY THE EGRESS GATEWAY (in recentRelayFailures).

  b) The manual archive download:
         https://github.com/SigNoz/foundry/releases/latest/download/
             foundry_linux_amd64.tar.gz
     `github.com/SigNoz/foundry` returns 403 — but NOT from the egress gateway.

CORRECTING THE EARLIER EVIDENCE: those are two separate controls, and the
previous diagnosis conflated them.

    https://github.com/akashbichukale111/devguard-ai   200   (this session's repo)
    https://github.com/SigNoz/foundry                  403
    https://github.com/torvalds/linux                  403

    403 body: {"message":"GitHub access to this repository is not enabled for
               this session. Use add_repo to request access. ..."}

    github.com present in the gateway's recentRelayFailures?   FALSE

So the github.com 403 is the SESSION REPO-SCOPE control, not the egress
allowlist. Its remedy is `add_repo`, not an allowlist entry. Note also that
`raw.githubusercontent.com` is NOT subject to it — SigNoz's own README and
docs were fetched from there at HTTP 200 during this investigation.

SigNoz Cloud is not an escape either: `ingest.us.signoz.cloud`, `us.signoz.cloud`,
`signoz.io` and `www.signoz.io` are all denied by the gateway.

  registry.npmjs.org — but neither of those proves Docker Hub's CDN is
  reachable from a runner, and no workflow here has ever pulled an image. To
  find out, one step in a scratch workflow settles it:

      - run: docker pull signoz/signoz:latest

  Codespaces: not applicable, none is in use.

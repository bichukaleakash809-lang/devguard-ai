2. THE DASHBOARD DEFECT — PROVEN BEFORE IT WAS FIXED
--------------------------------------------------------------------------------

SigNoz stores OTel metric names VERBATIM. It does not translate dots to
underscores. Ground truth, read straight out of the metrics store:

    $ SELECT DISTINCT metric_name FROM signoz_metrics.distributed_time_series_v4
    devguard.cache.miss_total          <- dots preserved
    devguard.llm.exceptions_total
    http.server.duration.bucket
    http.server.request.size.count
    ...
    signoz_calls_total                 <- only SigNoz's OWN metrics use underscores

`dashboard.json` referenced ten metric names, all with underscores. How many of
them exist in the metrics store:

    $ SELECT count() FROM signoz_metrics.distributed_time_series_v4
      WHERE metric_name IN ('devguard_cache_hit_total','devguard_cache_miss_total',
        'devguard_circuit_breaker_state_changes_total','devguard_llm_cost_per_request',
        'devguard_llm_exceptions_total','devguard_llm_tokens_total',
        'devguard_scan_latency', ...)
    0

**Zero.** Every metric panel on the shipped dashboard was dead — not "empty
because there is no traffic", but querying names that can never exist.

A NOTE ON HOW THIS WAS *NOT* PROVEN. An attempt to demonstrate the same thing
through SigNoz's /api/v5/query_range returned 0 datapoints for the underscore
name AND the dotted name — which looked like confirmation. It was not: the same
harness also returned 0 for `signoz_calls_total`, a metric that certainly has
data, so the query shape was simply wrong. That result was discarded rather than
reported. The ClickHouse query above is the evidence; the API probe is not.

3. THE FIX
--------------------------------------------------------------------------------

(a) METRIC NAMES. The 12 real names were extracted from the source of truth —
    the `_meter.create_*(name=...)` calls in backend/core/telemetry.py — and each
    underscore reference was rewritten to the dotted name, but ONLY where the
    dotted name is one the code actually emits. Nothing was renamed on a guess.

        devguard_scan_latency                        -> devguard.scan.latency          x3
        devguard_llm_cost_per_request                -> devguard.llm.cost_per_request  x2
        devguard_llm_tokens_total                    -> devguard.llm.tokens_total      x1
        devguard_llm_exceptions_total                -> devguard.llm.exceptions_total  x1
        devguard_circuit_breaker_state_changes_total -> devguard.circuit_breaker.state_changes_total x1
        devguard_cache_hit_total                     -> devguard.cache.hit_total       x1
        devguard_cache_miss_total                    -> devguard.cache.miss_total      x1

    Applied as a textual replacement of exact quoted names so the diff is 10
    lines and nothing else in the file moved.

(b) ONE PANEL DELETED. "RAG Context-K Adaptation Frequency" queried the span
    attribute `rag.context_k_adjusted`. That attribute is **absent from the entire
    codebase**:

        $ grep -rn "rag.context_k_adjusted" backend/ --include=*.py
        (no match)

    It corresponds to the Pattern-Learning Agent, which README already documents
    as not firing. A panel that can never populate is the dashboard equivalent of
    an overclaim, so it was removed (widget + layout entry, no dangling ids:
    widgets 10 -> 9). It should come back in the same commit that wires the loop.

(c) THREE PANELS DELIBERATELY LEFT ALONE. "Adaptive Routing Overrides",
    "Postmortem Agent Triggers" and the trace-based half of the dashboard use
    `dataSource: traces`, not metrics — they query span attributes, which is
    structurally correct. Their attributes were checked and DO exist in the code:

        routing.override_reason      ai_agent.py:868, :876
        postmortem.text              resilience.py:293
        breaker.name                 resilience.py:188, :292
        circuit_breaker.postmortem   resilience.py:290

    They return nothing today only because those code paths need a completed
    scan. That is a data gap, not a wiring defect, so nothing was changed.

5. §6.6 ALERTS — THREE RULES SHIPPED, APPLIED AND VERIFIED
--------------------------------------------------------------------------------

STARTING STATE: no alert rule existed.

    $ GET /api/v1/rules
    {"status":"success","data":[]}

WHAT alerts.md USED TO SAY, and why it was wrong. It specified three rules built
on three metrics:

    devguard_slo_compliance_pct     DOES NOT EXIST anywhere in the codebase
    devguard_circuit_breaker_state  DOES NOT EXIST
    devguard_llm_cost_usd_total     DOES NOT EXIST (the real one is
                                    devguard.llm.cost_total)

The file admitted this only in a soft aside ("assumes one corresponding OTel
metric is emitted ... not shown here"). Anyone following it would have built
three alerts that never fire. Rewritten so every rule targets a metric that
genuinely exists, and TWO OF THE THREE HAD TO CHANGE MEANING, not just names:

  * "SLO Compliance Degradation" -> "LLM error burst". There is no SLO metric.
    Nothing exports the calculation behind /slo-status.
  * "Circuit Breaker Stuck Open" -> "Circuit breaker flapping". The old rule
    needed a breaker-state GAUGE (0/1/2) to assert "held OPEN for 60s". Only a
    transition COUNTER is emitted, and a counter cannot express "is currently
    open" -- only "changed state N times". Writing the original rule would have
    meant claiming a detection that is not possible with the data.
  * "Cost Budget Exceeded" survives, with the correct counter name.

HOW THE SCHEMA WAS RECOVERED. This is the part that took the work, and the dead
ends are recorded because they are what makes the answer trustworthy.

  DEAD END 1 -- POST /api/v1/rules. Accepts the request and rejects it with one
  opaque line, no field named:
      {"errorType":"bad_data","error":"alert rule is not valid"}
  Tried: builder-style compositeQuery; the same with "version" v3/v4/v5; a
  promql_rule variant. All refused identically. Unsolvable by iteration.

  DEAD END 2 -- driving the UI. The metric picker is #rc_select_2 inside
  .metric-name-selector (not a plain <input>, which is why an earlier attempt
  could not find it). Once found, the metric SELECTED correctly -- but
  "Save Alert Rule" stayed disabled, and so did "Test Notification", from the
  moment the form loaded.

  THE BREAKTHROUGH -- SigNoz ships its own SOURCE MAPS in the container
  (/etc/signoz/web/assets/*.js.map). Two files answered everything:

    src/types/api/alerts/alertTypesV2.ts
        defines PostableAlertRuleV2 exactly: schemaVersion "v2alpha1",
        condition.thresholds.spec[] as BasicThreshold
        {name,target,matchType,op,channels[],targetUnit},
        evaluation.kind / evaluation.spec.

    src/container/CreateAlertV2/Footer/utils.tsx
        validateCreateAlertState() -- the exact reason Save was disabled:
        every threshold needs a label AND at least one channel, UNLESS
        notificationSettings.routingPolicies is enabled. On a clean install with
        no notification channel configured, the button can never enable.

  AND -- POST /api/v2/rules RETURNS FIELD-LEVEL ERRORS, which v1 does not:
      "condition.compositeQuery.queries: must have at least one query"
      "notificationSettings: field is required for schemaVersion \"v2alpha1\""

TWO THINGS THAT ARE EASY TO GET WRONG, and both bit here:

  * condition.compositeQuery takes a **queries ENVELOPE array**
    ([{"type":"builder_query","spec":{...}}]), NOT the dashboard's
    builder.queryData shape. They are not interchangeable.
  * notificationSettings is REQUIRED. Setting usePolicy:true routes through
    SigNoz's routing policies instead of naming a channel -- which is what lets
    these rules apply on a fresh instance with NO channel configured.

deployment step for whoever runs this, not a defect in the assets.

# PART 0 — VERDICT ON YOUR FOUR BLOCKS

**Short answer: three of the four make the project meaningfully stronger. One of them can lose you the hackathon by eating the schedule. All four need hardening before they go in, because as written each has at least one clause that quietly invites fabrication or unbounded scope.**

### §5.6 Live Agent Conversation — **KEEP. Strongest of the four.**
This is the single best idea in your list. "AI operations center, not a chatbot" is exactly the right instinct, and it converts the multi-agent architecture from something a judge has to read code to believe into something they see in five seconds.

**The trap:** if those sentences are generated by an LLM as flavour text, it is theatre with extra steps — and a maintainer judge will ask "is the agent saying that, or is a model narrating what you wish it said?" The fix is that every line must be **rendered from the agent's actual structured output plus real evidence IDs**, via a deterministic template. The conversation is a *view* of the evidence ledger, never a second source of truth. Hardened version in Part A.

### §7.4 Live Platform Status Bar — **KEEP. Highest value per hour of any item here.**
It deletes a LAW 3 violation (the fake `Threats Blocked: 24,068` ticker) and replaces it with something that is both honest and more impressive. Real status beats invented scale with any competent judge.

**Two traps:** `Agents 11 Running` is misleading if they are idle — that is an invented-metric pattern in disguise. And a status bar that polls five dependencies on every render will hammer your own backend during the demo. Hardened version in Part A.

### §8.x 3D Knowledge Graph — **CUT TO A TIER-1 CORE. This is the one that can sink you.**
Everything on that list — GPU rendering, camera transitions, focus mode, fullscreen, search, pan, zoom, replay, ownership indicators — is 3 to 5 days of frontend work on its own. You have days, not weeks, and the criteria do not award points for rendering technique. Under LAW 2, most of that list has to justify itself against "which criterion does this raise," and the honest answer for camera transitions is "none."

There is also a design argument, not just a schedule one: **3D is usually worse than 2D for reading lineage.** Depth occlusion hides edges, labels rotate out of legibility, and at 1080p video compression a rotating 3D graph turns to mush. The thing that actually makes a judge lean forward is not the third dimension — it is **the graph animating in lockstep with the reasoning**: node ignites, edge traverses, evidence chip appears, timeline advances. That choreography works perfectly in 2D and costs a fraction as much.

Recommendation: build a **WebGL-accelerated animated 2D force-directed graph** with your full choreography (Tier 1), add focus/search/fullscreen if time allows (Tier 2), and treat 3D as a ceiling item that almost certainly never gets built (Tier 3). You lose nothing a judge scores and you buy back two days for write-back and the submission package. Tiered spec in Part B.

### §13.1 Execution Discipline — **KEEP. No objection to the substance.**
This is correct and it is the rule most people skip. It needs three additions: a hard definition of what "verify" means (otherwise the model marks its own homework green), a rollback procedure, and an explicit git-safety clause. Hardened version in Part A.

### The gap none of the four covers
Your four blocks are all about **showing**. What is missing is **explaining** — the drill-down from any agent message to the exact prompt, tool calls, evidence and cost that produced it. That single feature is what separates "impressive demo" from "system I would trust," it is cheap because the proof pack already holds the data, and almost nobody will build it. It is Part C, §5.7, and if you only add one thing from this entire document, add that.

## §5.6 — LIVE AGENT CONVERSATION (Operations Center, not chatbot)

The goal is not animated panels. The goal is that a judge watching for ten seconds concludes — correctly — that real agents are collaborating right now.

**The rendering rule that makes this honest:**
Every message is produced by a **deterministic template** filled from the agent's real structured output. No message is ever free-form LLM narration. If the template has no real value to fill a slot, the message is not emitted.

```
AgentMessage {
  ts              UTC, from the real clock
  agent           canonical id (see §6.0 roster)
  display_name    e.g. "Cartographer"
  state           DISPATCHED | EXECUTING | COMPLETE | REFUSED | ERROR | DEGRADED
  text            rendered from template + real values
  evidence_ids    [ ... ]        # required for any factual claim
  trace_id        optional, links to SigNoz
  duration_ms     real
  tokens, cost    real, when the agent used a model
  data_source     LIVE | REPLAY | SIMULATED
}
```

**Template examples** (values in `{}` come from the real response — never hard-coded):
- Watcher: `Schema drift detected on {dataset}. {n} runtime failures in {window}.`
- Cartographer: `Resolved {dataset} to {urn}. {n} downstream assets depend on it.`
- Pathfinder: `Blast radius: {n} assets across {k} hops, terminating at {terminal_entity}.`
- Archivist: `{Found prior verified incident {doc_urn} | No prior verified incidents for this asset.}`
- Diagnostician: `Root cause: column {old} renamed to {new}. Chain: {evidence_ids}.`
- Diagnostician (refusal): `Insufficient evidence — no {missing_class} correlates with any graph change. Stopping.`
- Scribe: `Knowledge package written: incident {urn}, runbook {urn}, {n} annotations.`

**Rules:**
- Every message derives from actual execution. A message with no backing evidence is a defect, not a cosmetic issue.
- **Failure and refusal messages are rendered with the same care as success messages.** The refusal line is a headline demo beat, not an error state.
- Live mode streams messages as they occur; the animation duration *is* the execution duration.
- Replay mode carries a persistent banner: `REPLAY OF PREVIOUS EXECUTION — <run-id>`, and replays with the original inter-message timings.
- The conversation is a **view** over the evidence ledger. If the two ever disagree, the ledger is right and the conversation has a bug.
- No agent ever addresses the user, asks a question, or uses first-person pleasantries. Operations centers log; they do not chat.
- Every message row is clickable → the drill-down in §5.7.

## §7.4 — LIVE PLATFORM STATUS BAR

Replaces the fabricated counter on the home page. Every value comes from a real check.

**Backend:** one aggregate endpoint `GET /health/platform` returning per-dependency status, each with `status`, `checked_at`, `latency_ms`, `detail`. Checks run **server-side on a cache with a short TTL** — the frontend polls one endpoint, never five. Every check has a hard timeout; a slow dependency reports `DEGRADED`, it does not hang the bar.

| Field | Source | Never |
|---|---|---|
| Backend | self | — |
| DataHub | real GMS ping | assumed from config |
| SigNoz | real collector/query ping | assumed |
| Enterprise | module registered + last successful run | "running" when idle |
| Agents | `{n} registered · {m} active now` | a bare "11 running" |
| Last incident | real store, or `None yet` | invented recency |
| Telemetry | `LIVE` / `LOCAL SHADOW` / `OFF` | `LIVE` unless a span actually exported |

**Rules:**
- States: 🟢 `Connected` · 🟡 `Simulated` / `Degraded` · 🔴 `Offline` · ⚪ `N/A`.
- Colour is never the only signal — always colour **plus** the word (accessibility, and it survives video compression).
- Unknown renders `N/A`. Never invent uptime, request counts, users, latency, or throughput.
- Auto-refresh on a sane interval, with backoff when a dependency is down. Never block page render on it; the bar streams in.
- Fixed height reserved from first paint — the bar must never cause layout shift.
- Clicking any item opens the detail: last check time, latency, and the exact error if offline.

## §13.1 — EXECUTION DISCIPLINE

Claude Code never rebuilds the repository in one step. Every phase follows:

```
AUDIT → REPORT → WAIT FOR HUMAN APPROVAL → REPAIR → COMMIT → VERIFY → NEXT PHASE
```

**What "VERIFY" means** — a phase is verified only when **all** of these hold, with output pasted into the phase report:
1. The build passes (backend imports, `npm run build`, zero TypeScript errors).
2. Tests for the touched area pass, and at least one test covers the new behaviour.
3. The behaviour was **executed**, not merely implemented, and the real output is in the report.
4. No previously working screen or endpoint regressed — name which ones you checked and how.
5. An artifact exists on disk (log, screenshot, captured response) that a third party could inspect.

A phase where 1–5 cannot all be satisfied is **reported as blocked**. It is never marked complete with a caveat.

**Rules:**
- Never skip verification. Never continue past a failed verification.
- Never perform a destructive refactor, mass rename, file deletion, or dependency removal without explicit approval.
- One branch per phase; merge only after verification. **Never `git push --force`, never rewrite published history, never `git checkout .` or `git clean` over uncommitted work.**
- Every phase ends with a commit and a short progress report; the completed phase is the baseline for the next.
- **Rollback:** if a phase breaks something that previously worked and cannot be fixed within the phase, revert to the prior baseline commit, report what happened, and stop. A clean revert is a good outcome; a broken main branch two days before the deadline is not.
- If uncertainty exists, stop and ask. A question costs minutes; a wrong guess compounded over three phases costs a day.
- Never mark your own work green because the code looks correct. Green comes from output, not from confidence.

## §8.x — THE LIVING LINEAGE GRAPH

The graph is the visual centrepiece of the Enterprise module and the anchor shot of the demo video. It is not a dependency diagram; it is an operational surface that moves in lockstep with the agents' reasoning.

**Technology:** WebGL-accelerated **2D** force-directed graph. 2D is the deliberate choice — depth occlusion hides exactly the edges a judge needs to see, and rotating 3D labels do not survive video compression. Legibility beats dimensionality.

### TIER 1 — required (build this; roughly one day)
- Real DataHub lineage, column-level where available. **Graph-confirmed edges solid; inferred edges dashed and labelled** — never silently mixed.
- **The choreography, synchronised to real agent events:**
  `node ignites → edge traverses → evidence chip appears in the ledger → timeline advances → knowledge package grows → write-back animation fires`
  Each step is triggered by an actual event, so the animation cannot run ahead of the truth.
- Pulse on the node an agent is currently reasoning about.
- Root cause node highlighted red; recovery path highlighted green; terminal ML model node visually distinct.
- Node click → entity detail: URN, owner, schema fields, evidence attached, link into DataHub.
- Legible at 1080p with the browser at default zoom — check this by screenshotting, not by looking at your own monitor.

### TIER 2 — only if Tier 1 is frozen and the write-back is done
Pan · zoom · search/filter · focus mode (dim everything outside N hops) · fullscreen · agent-ownership indicators · replay scrubbing over the graph.

### TIER 3 — almost certainly never
3D rendering · cinematic camera transitions · physics-based layout tuning. If you are building these, something scored is being neglected.

**Performance budget:** 60fps with 200 nodes; graceful degradation (auto-collapse to summary nodes) beyond that; no main-thread blocking during animation; respects `prefers-reduced-motion` by jumping to end states instead of animating.

## §5.7 — "EXPLAIN THIS DECISION" DRILL-DOWN *(highest value in this document)*

Any agent message, evidence chip, graph node, or write-back row is clickable and opens a panel showing exactly how that conclusion was reached:

- the **prompt actually sent** (with untrusted catalog text visibly fenced)
- every **tool call**: name, arguments, latency, and the raw response
- the **evidence chain** consumed and produced, each item traceable to the proof pack
- **model, tokens, cost** for that step
- the **trace link** into SigNoz
- for a refusal: which evidence class was missing and which rule fired

**Why this wins:** every competing project is a black box that asks to be trusted. This one shows its work on demand. It costs little — the proof pack already contains all of it — and it is the difference between a judge thinking "nice demo" and "I could operate this." It also makes the video trivially strong: one click, and the claim is substantiated on camera.

## §8.y — TIME-TRAVEL SCRUBBER

One horizontal scrubber over the incident timeline. Dragging it moves the **entire screen** to that moment: the graph shows what was known then, the conversation truncates, the evidence ledger shows only what had been collected, the write-back panel shows pending state.

This is cheap once replay exists (the proof pack is already an ordered event log), and it does three things at once: it makes the demo video easy to cut, it lets a judge inspect any moment without re-running anything, and it demonstrates that the system's state is genuinely reconstructible from its evidence — which is the strongest possible argument that the evidence is real.

## §7.7 — DESIGN TOKEN SPEC (make "premium" falsifiable)

"Apple/Vercel/Linear quality" is not a requirement until it is measurable. Bind it:

- **Type:** one family for UI (geometric sans), one mono for all machine values (URNs, IDs, durations, costs). A 6-step scale, no ad-hoc sizes. Tabular numerals everywhere a number can change, so digits do not jitter during live updates.
- **Space:** 4px base, 8-step scale, nothing off-scale. Generous outer padding; dense inner data.
- **Colour:** one neutral ramp plus **at most three** accents visible at once. Semantic only: green = verified/healthy, amber = simulated/degraded, red = fault/root cause, violet = agent activity. No decorative gradients behind text, ever.
- **Elevation:** 3 levels maximum. Borders over shadows on dark surfaces.
- **Motion:** 120ms micro, 240ms panel, 400ms graph. One easing curve. Motion always communicates state change — never decorates. `prefers-reduced-motion` fully respected.
- **Density:** this is an instrument panel, not a landing page. Whitespace between groups, tightness within them.
- **The one-frame test:** every screen must be legible as a single 1080p video frame. If a judge has to squint, it fails, regardless of how good it looks at full monitor size.

## §7.8 — EMPTY STATES, ERRORS, AND FIRST RUN

Most hackathon UIs look broken before you click anything. Yours must not.

- Every panel has a designed empty state that explains what will appear there and how to make it appear.
- The home page offers **"Run sample incident"** as a primary action that works with zero configuration — because most judges will never set up DataHub, and this is what they will click.
- Every error state names what failed, what it means, and what to do next. No blank panels, no silent console errors, no infinite spinners — every async surface has a timeout and a visible failed state.
- First-run experience is tested on a machine that has never seen the project.
